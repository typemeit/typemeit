## Foundation Models latency research — findings

**1. Guided generation overhead.** `respond(to:generating:)` injects the type's JSON schema into the prompt by default (`includeSchemaInPrompt` defaults to `true`) to bias the model toward that shape — official doc: "If true, injects the schema into the prompt to bias the model" (developer.apple.com/documentation/foundationmodels/languagemodelsession/respond(generating:includeschemainprompt:options:prompt:)). Apple's guided-generation guide states long `@Guide` descriptions "take up additional context size and can introduce latency" (developer.apple.com/documentation/foundationmodels/generating-swift-data-structures-with-guided-generation). `includeSchemaInPrompt: false` is safe only once the model has already seen the format (e.g., earlier turns in the same session, or restated in your instructions) — otherwise output quality degrades. No official percentage overhead is published; a commonly-repeated "10–20% latency savings" figure could not be traced to an Apple source — **unverified**. For a 1-field struct like `CleanedTranscript`, schema-token overhead is inherently small regardless.

**2. prewarm() / prewarm(promptPrefix:).** Confirmed via Apple's own doc (developer.apple.com/documentation/foundationmodels/optimizing-key-value-caching-in-language-model-sessions): the KV cache covers instructions + tool definitions + transcript, in that order; `prewarm(promptPrefix:)` precomputes that prefix before the first `respond()`/`streamResponse()` call. Apple recommends calling it 1–2 seconds ahead of the request. Appending content preserves the cache; editing/removing earlier content invalidates everything after it. **A new `LanguageModelSession`, even with identical instructions, never reuses a prior session's cache** — "each new session starts without a KV cache" — there is no cross-session or system-wide KV cache. Restoring from a saved `transcript` + `prewarm()` re-hydrates proportional to transcript size, not instantly.

**3. Decode speed / TTFT.** Apple's only published figures are from the original 2024 on-device 3B model announcement: **~30 tokens/sec generation** and **~0.6 ms per prompt token** TTFT, measured on iPhone 15 Pro (machinelearning.apple.com/research/introducing-apple-foundation-models). No updated tokens/sec figure has been published for the 2025/2026 model revisions — **unverified/pending** (Apple's June 2026 post on the new "AFM 3 Core"/"AFM 3 Core Advanced" models promised a benchmark-bearing tech report "later this summer 2026"; none surfaced in this research as of Sept 2026: machinelearning.apple.com/research/introducing-third-generation-of-apple-foundation-models). Arithmetic from Apple's two published numbers: prefill for ~550 tokens (450 instructions + ~100-word transcript) ≈ 330 ms; decode of 20–150 output tokens at 30 tok/s ≈ 0.7–5 s. **Decode (output length) dominates**, matching your measured length-scaling.

**4. Streaming.** `streamResponse` yields `T.PartiallyGenerated` snapshots as generation proceeds (developer.apple.com/documentation/foundationmodels/languagemodelsession). It does not reduce total compute/decode time — no Apple source claims otherwise — it only improves *perceived* latency and lets you consume/paste partial text before the full struct completes. Cancelling the stream early (dropping the Task) stops generation; the session then waits for wind-down before the next call — this is standard Swift structured-concurrency cancellation rather than a documented FM-specific guarantee — **partially unverified**.

**5. GenerationOptions.** `maximumResponseTokens` directly caps decode length (a real speed lever) but Apple warns a too-strict cap "can lead to the model producing malformed results" (developer.apple.com/documentation/foundationmodels/generationoptions) — risky with guided generation since truncation can break parsing. `sampling:` was renamed to `samplingMode:` in the OS 27 SDK (back-deployed to OS 26); purely a naming change, old initializer deprecated, no behavior/speed difference. `temperature` and sampling-mode choice (greedy vs. top-k/top-p) act only on already-computed logits — no evidence either affects per-token latency.

**6. Concurrency.** A single session serializes its own calls — `respond(to:)` throws if called again before the prior call finishes (check `session.isResponding`). Whether two *separate* sessions get true parallel throughput on-device, or are arbitrated/serialized by a shared system model process, is **not documented by Apple and could not be verified** (only a third-party Medium writeup addresses session mechanics: medium.com/@luizfernandosalvaterra/inside-foundationmodels-how-sessions-actually-work-1a250bb30110). Treat chunk-and-parallelize as untested for this framework.

**7. Custom adapters.** Training: Python toolkit, rank-32 LoRA, needs a Mac (Apple silicon, 32GB+ RAM) or Linux GPU box; 100–1,000 examples for basic tasks, 5,000+ for complex ones (developer.apple.com/apple-intelligence/foundation-models-adapter). Shipping requires the `com.apple.developer.foundation-model-adapter` entitlement (not needed for training/local testing), requested by the Developer Program account holder. Adapters are ~160 MB, distributed via Background Assets (never bundled), and **must be retrained for every base-model/OS version** — a v26.0.0 toolkit adapter is incompatible with OS 27+. An optional trained "draft model" enables speculative decoding for a latency win; without it, no speedup is implied. **Whether the entitlement/Background Assets path works for a non-App-Store, Developer-ID-signed app is not addressed anywhere found — unverified.**

**8. WWDC 2026 (macOS 27 cycle).** On-device model "rebuilt from the ground up," better logic/tool-calling, refined guardrails with fewer false positives; new `model.contextSize` / `model.tokenCount(for:)` APIs (back-deployed to 26.4); on-device context grew from 4,096 (macOS 26.0) to 8,192 tokens; new Private Cloud Compute model option (32K context, optional reasoning levels) callable through the same API; image-input support; framework going open source; `fm` CLI on macOS 27 (developer.apple.com/videos/play/wwdc2026/241/). No raw decode-speed number was published alongside these changes — **unverified**.

**9. useCase / guardrails.** `.contentTagging` is a specialized adapter for short tag/entity/topic output (1-few words), not applicable to full-transcript cleanup (developer.apple.com/documentation/foundationmodels/systemlanguagemodel/usecase). No published speed delta vs. `.general` beyond naturally shorter outputs. `.permissiveContentTransformations` vs `.default` differ in refusal thresholds for text-transform tasks, not documented decode speed — **no evidence of a speed difference either way**.

**10. Editing/rewriting guidance.** Apple's official guide (developer.apple.com/documentation/foundationmodels/prompting-an-on-device-foundation-model): keep prompts to 1–3 paragraphs, use direct imperative instructions, prefer a single request over multi-step chains ("multiple requests can result in longer inference time"), use 2–15 short few-shot examples (not more), and give the model a dedicated reasoning field if you need step-by-step behavior so it doesn't leak into your `@Generable` output. The model "does well with rewriting short fragments" and guardrails should be relaxed via `.permissiveContentTransformations` for exactly this transform-style task — which your app already does.

## Top 5 latency levers, ranked

1. **Reuse one long-lived `LanguageModelSession` across dictations instead of a fresh session per cleanup.** Confirmed: new sessions never inherit a KV cache, so every fresh session likely re-pays instruction prefill unless `prewarm` had enough lead time — this best explains your ~0.8s floor on 1–5 word transcripts. Append-only turns preserve cache; trim only when nearing the 4,096-token ceiling (source: Apple's KV-caching doc, §2 above).
2. **Use streaming to reduce perceived/paste latency on long transcripts**, especially the 100+ word (3.4s) bucket — start consuming `cleanedText` as it forms rather than waiting for the whole struct, even though total compute is unchanged.
3. **Cap `maximumResponseTokens` proportional to input length** to bound the runaway tail, while testing carefully that guided-generation output isn't truncated mid-schema.
4. **Once sessions are reused (lever 1), test `includeSchemaInPrompt: false` on turns after the first** — the schema will already be established in transcript history. Low individual impact given your struct is a single field, but nearly free to try.
5. **Do not invest in parallel-session chunking until tested on-device** — concurrency behavior across sessions is undocumented and unverified; it may simply serialize and add duplicate instruction-prefill cost. Similarly, custom adapters (lever candidate) are a heavy, uncertain-payoff investment (160MB, per-OS retraining forever, entitlement approval, unverified Developer-ID eligibility) — revisit only after 1–4 plateau.
