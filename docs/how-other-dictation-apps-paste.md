# How other dictation apps paste into the focused app

Type Me It delivers a transcript by putting it on the clipboard, posting Cmd+V
and putting the old clipboard back (`TypeMeIt/Output.swift`). Users report three
failures: the paste lands nothing, the previous clipboard is pasted instead of
the transcript, and the app cannot always tell whether a text field has focus.
This note records how ten open-source dictation apps handle the same job, what
their issue trackers say about the same three failures, and what the macOS
pasteboard API allows. Read against each project's source at a pinned commit
and its GitHub issues. Written September 2026.

## Where Type Me It stands

- `Output.paste` (`TypeMeIt/Output.swift` 23–70): saves the clipboard's text,
  or an image when there is no text (25–28); writes the transcript and records
  `changeCount` (30–33); sleeps `Fixed.pasteDelayBeforeMs` = 60 ms
  (`TypeMeIt/Settings.swift` 191); posts V key-down and key-up with
  `.maskCommand` to `.cghidEventTap` from a `nil` event source, with no
  Command key events of their own (8–16, 36); sleeps `Fixed.pasteDelayAfterMs`
  = 60 ms (192); logs, but does not act on, a changed `changeCount` (42–44);
  clears and restores unconditionally (45–50). Auto-submit posts Return
  `Fixed.autoSubmitDelayMs` = 50 ms later (53–61).
- The return value is whether `CGEvent(keyboardEventSource:...)` returned an
  event (9–10, 69). It does not report whether the system delivered it.
- `Focus.focusedElementIsTextInput` (`TypeMeIt/Focus.swift` 54–106) reads
  `kAXFocusedUIElement` from the system-wide element, then from the frontmost
  app (60–83), and classifies the role as text input when it is
  AXTextField/AXTextArea/AXComboBox/AXSearchField or `AXValue` is settable
  (18, 26–28, 97–101). `nil` when nothing answers (85–89).
- `Pipeline` (`TypeMeIt/Pipeline.swift` 272–296) runs the focus check, pastes
  regardless of its answer, and shows the copy prompt when the focus check
  returned `false` or no event could be created (289–292).
- Secure input is polled once a second for the menu (`TypeMeIt/TypeMeItApp.swift`
  233–236) and logged at paste time (`Output.swift` 39), but the paste is not
  gated on it.
- A debug-only read-back checks whether the transcript, or the previous
  clipboard text, is in the field afterwards (`Output.swift` 92–126).

## VoiceInk (Swift)

Source at commit `832d212`, 2026-09. [CursorPaster][vi-paster],
[ClipboardManager][vi-clipmgr], [SettingsView][vi-settings],
[AppDefaults][vi-defaults], [TranscriptionDelivery][vi-delivery].

- Mechanism: a user-selectable "Paste Method". Default posts four CGEvents
  (Command down, V down, V up, Command up) from a `.privateState` source to
  `.cghidEventTap`, 10 ms apart ([CursorPaster][vi-paster] 20–21, 184–214).
  "AppleScript" runs `keystroke "v" using command down`, or `key code 9` on
  layouts named "… QWERTY ⌘" (144–178). The settings tip: "AppleScript can help
  when custom keyboard layouts do not paste correctly"
  ([SettingsView][vi-settings] 151–171).
- Clipboard: 100 ms before Cmd+V (20, 64). Restore is a setting, "Keep
  Clipboard Content", on by default with a 2 s delay
  ([AppDefaults][vi-defaults] 34–35); the picker offers 250 ms to 5 s
  ([SettingsView][vi-settings] 140–148) and the code floors it at 250 ms
  (22, 105–108). The restore only runs if the clipboard still holds the
  transcript and a per-paste UUID under the private type
  `com.VoiceInk.PasteSession` (99–130, [ClipboardManager][vi-clipmgr] 5, 31).
  The write also carries `org.nspasteboard.source`, and when a restore is
  planned, `TransientType` and `AutoGeneratedType` (6–8, 22–29). The snapshot
  keeps every pasteboard item and type (79–88, 132–140).
- Focus: none before pasting. The only `kAXFocused…` query in the tree reads
  the focused window for screen capture; selected text is read through the
  SelectedTextKit library as prompt context. Auto-send waits 500 ms after the
  paste task ([TranscriptionDelivery][vi-delivery] 164–173).
- Accessibility: `AXIsProcessTrusted()` is checked before posting CGEvents
  (185). No secure-input check.
- History of the delays: 600 ms restore ([99dfb74][vi-c-600], 2025-08); 900 ms
  with a `TransientType` marker and a 50 ms pre-paste dispatch
  ([7feef2b][vi-c-transient], 2025-11); restore off by default, with an
  optional delay ([baae439][vi-c-preserve], 2025-12); restore on by default at
  1 s ([05cc14a][vi-c-1s], 2026-01); sub-second choices added
  ([46c5ed7][vi-c-subsecond], 2026-02); the UUID session check, a 100 ms
  pre-paste wait and a 1 s floor ([caca8c4][vi-c-session], 2026-05); floor
  lowered to 250 ms the same day ([9d41f5e][vi-c-250]).
- Issues on the old clipboard being pasted: [#415][vi-415] (2025-12, restore at
  1 s ran before the app read the pasteboard; the reporter logged
  `changeCount` to show it) was answered with the restore toggle and delay.
  [#722][vi-722] (2026-05, v1.77): 250 ms and 500 ms pasted the old clipboard,
  1 s worked; closed after [caca8c4][vi-c-session]. [#432][vi-432] and
  [#646][vi-646] are the opposite complaint, the transcript staying on the
  clipboard, answered with the same setting.
- Focus detection was tried and removed. [05806f4][vi-c-fallback] (2025-06-30)
  gated the paste on the frontmost app's `kAXFocusedUIElement` having a
  settable `AXValue` and showed a fallback window otherwise. Two days later
  the paste ran unconditionally and the window became an extra
  ([f9d6352][vi-c-always]); [#159][vi-159] reported the window on every
  dictation, and the maintainer wrote that it "will automatically show up on
  most electron based apps because there is no way to determine if we are in
  text field or not using accessibility APIs"; the window was removed in
  [8f7411d][vi-c-remove] (2025-07-07) and its files in
  [a762070][vi-c-delete].
- Layouts: [cbf7f60][vi-c-layout] (2026-02) records that a `.hidSystemState`
  source made virtual key 9 misfire on Dvorak and that `keystroke "v"` maps to
  the wrong physical key; it switched to `.privateState`. Input-source
  switching was dropped for the AppleScript option in [063e8ac][vi-c-as].
- Terminals: [#610][vi-610] found the 50 ms gap between Cmd+V and Enter too
  short for Terminal, iTerm2 and Warp; [a75ef6f][vi-c-autosend] raised it to
  500 ms ("paste travels through PTY/readline and can take 200-350ms").

## Hex (Swift, TCA)

Source at commit `f58d52c`, 2026-09. [PasteboardClient][hex-pb],
[HexSettings][hex-settings], [GeneralSectionView][hex-general].

- Mechanism: "Use clipboard to insert" (default on, [HexSettings][hex-settings]
  67) posts Command down, V down, V up, Command up from a
  `.combinedSessionState` source to `.cghidEventTap`, with the V key code
  resolved through the Sauce library for the current layout
  ([PasteboardClient][hex-pb] 302–325). Off, it runs AppleScript
  `keystroke "<text>"` for the whole transcript (84–90, 333–341); the settings
  copy calls this "Slower, but doesn't need to restore clipboard"
  ([GeneralSectionView][hex-general] 38–50).
- Fallback chain: `cmdV`, then clicking Edit › Paste through System Events,
  then `AXUIElementSetAttributeValue(kAXSelectedTextAttribute)` on the focused
  element (270–297, 350–379). `postCmdV` returns `true` unconditionally (318),
  so the second and third strategies never run. Until [de0e9be][hex-c-order]
  (2025-11) the menu click ran first and Cmd+V was the fallback
  ([17b4258][hex-c-menu], [bd740f6][hex-c-fix39]).
- Clipboard: before Cmd+V, it records `changeCount`, writes, and polls every
  5 ms for up to 150 ms until the count reaches the value it expects
  (236–266). Restore, only when "Copy to clipboard" is off, is a fixed 500 ms
  later with no ownership check (211–223); the delay was 100 ms until
  [68475f5][hex-c-500] (2025-11), whose comment names Claude and Warp as the
  slow readers. All pasteboard items and types are snapshotted (52–81).
- Focus: none. Secure input: none. `AXIsProcessTrusted` is only consulted by
  the hotkey monitor.
- Issues: [#42][hex-42] (2025-03) and [#69][hex-69] (Alfred, Raycast) reported
  the previous clipboard being pasted, including a password. Both were closed
  in 2025-11 citing the wait-for-`changeCount` write in
  [1b400ca][hex-c-harden] (the closing comment names changeset commit
  `2fbbe7a`). That fix covers the write racing the keystroke, not the restore
  racing the read. [#29][hex-29] and [#35][hex-35]: the menu-click route opened
  Xcode's Paste submenu instead of pasting. [#39][hex-39] asked for copy-only
  when no text field is available; a maintainer noted the menu route can read
  whether Paste is enabled, the keystroke route cannot. [#289][hex-289]
  (2026-08): typing mode fails silently under the App Sandbox because Apple
  Events to System Events need an entitlement. A comment on [#69][hex-69]
  reports the typing mode replaces non-Latin letters with "a".

## OpenSuperWhisper (Swift)

Source at commit `c8e6fe7`, 2026-09. [ClipboardUtil][osw-clip],
[IndicatorWindow][osw-indicator], [FocusUtils][osw-focus].

- Mechanism: V down and V up with `.maskCommand` from a
  `.combinedSessionState` source to `.cghidEventTap`, no Command key events
  ([ClipboardUtil][osw-clip] 72–100). The V key code comes from
  `UCKeyTranslate` over the current layout, with key code 9 for "QWERTY ⌘"
  layouts and non-Latin layouts (74–88, 102–166). Tests cover 19 layouts.
- Clipboard: no wait before Cmd+V. Restore after 1.5 s, and only if
  `changeCount` still equals the value read after the write (12, 43–66). The
  file comment: "Slow consumers (browsers, Electron apps) can service the
  synthesized Cmd+V long after the event is posted. Restoring the original
  clipboard earlier makes them paste the old contents instead of the
  transcription." Two settings pick paste-and-restore, paste-and-keep, or copy
  only ([IndicatorWindow][osw-indicator] 319–336). No transient marker.
- History: a synchronous 100 ms sleep before restore until
  [ffdc736][osw-c-async] (2026-07-04, made asynchronous, still 100 ms);
  [b590064][osw-c-15] the next day set 1.5 s and added the `changeCount`
  guard.
- Focus: AX is used only to place the recording indicator at the caret
  ([FocusUtils][osw-focus] 52–70, 160–183); the paste is not gated.
  Accessibility is checked at onboarding, not at paste. No secure-input check.
- Issues: [#153][osw-153] (2026-06, ChatGPT in a browser pasted the copied
  text instead of the transcript) closed after [b590064][osw-c-15].
  [PR #129][osw-pr129] (open) proposed 500 ms and describes the race; the
  maintainer asked for a delay that scales with CPU load. [PR #120][osw-pr120]
  proposed `.hidSystemState`, waiting for the hotkey's modifiers to be
  released, and 300 ms; its author closed it saying synthetic Cmd+V "is
  unreliable regardless of timing fixes" and that a fork uses
  `AXUIElementSetAttributeValue`. [#141][osw-141]: inside Parallels and VMware
  a lone V with the Command flag types "v"; the reporter asked for real
  Command key events and a longer restore. [#30][osw-30] (2025): "The
  application cannot insert text into a web page."

## Handy (Rust, Tauri)

Source at commit `db1aaac`, 2026-09. [clipboard.rs][handy-clip],
[input.rs][handy-input], [settings.rs][handy-settings],
[paste_tx/mod.rs][handy-tx], [paste_tx/macos.rs][handy-tx-mac].

- Mechanism: "Paste Method" setting: `CtrlV` (default on macOS), `Direct`
  (enigo `text()`, per-character), `None`, `ShiftInsert`, `CtrlShiftV`,
  `ExternalScript` ([settings.rs][handy-settings] 150–157, 217–224). Cmd+V is
  enigo Meta press, V click, 100 ms hold, Meta release
  ([input.rs][handy-input] 168–204); the V key code is resolved with
  `UCKeyTranslate` while Command is held (77–133). The hold came from
  [PR #165][handy-165] (2025-10) after reports of a bare "v" being typed
  ([#12][handy-12]).
- Legacy clipboard path: text, or an image when there is no text, is saved;
  sleep `paste_delay_ms`; chord; sleep `paste_delay_after_ms`; restore, or
  clear when nothing was saved ([clipboard.rs][handy-clip] 55–118). Both
  delays default to 60 ms ([settings.rs][handy-settings] 600–606), the same
  values as Type Me It. No `changeCount` guard. "Clipboard Handling" can
  leave the transcript on the clipboard instead (176–180, 859–861).
- Receipt-sequenced "reliable paste" (opt-in debug toggle, `reliable_paste`,
  [settings.rs][handy-settings] 480–484; added in [a70ac84][handy-c-tx],
  2026-07-31): the transcript is published with `declareTypes:owner:` as a
  promise, so AppKit calls the owner's `pasteboard:provideDataForType:` when a
  consumer reads the text; that call is the receipt
  ([paste_tx/macos.rs][handy-tx-mac] 1–13, 47–87, 283–297). Only receipts
  after the chord was injected count; the restore runs 200 ms after the last
  receipt (Chromium reads more than once), or after 8 s with no receipt, or
  500 ms if the chord could not be sent; it is skipped when `changeCount`
  moved or `pasteboardChangedOwner:` fired ([paste_tx/mod.rs][handy-tx] 18–32,
  50–63, 139–157; [macos.rs][handy-tx-mac] 157–177). Auto-submit Enter is sent
  only after a receipt (141–155). The write carries the three
  `org.nspasteboard` marker types so clipboard managers do not read it (36–40).
- Focus: none (no AX focused-element query in `src-tauri/src`). Secure input
  is detected for shortcuts, not for the paste
  ([secure_input.rs][handy-secure] 1–19).
- Issue [#502][handy-502] (open since 2025-12, 82 comments) is the
  old-clipboard-pasted report on macOS, Windows and Linux. A "paste delay"
  slider was added ([PR #694][handy-694], 2026-02); one reporter raised it in
  10 ms steps from 60 ms to 190 ms and still hit the bug; [PR #1465][handy-1465]
  applied the delay after the chord too and extended the slider to 500 ms,
  which its author needed under load; a contributor traced the race to the
  restore, not the write. The maintainer's later comment: "for the time being
  I'm out of ideas other than just configuring even longer delays". After the
  receipt build, one macOS user reported the bug gone after two days
  (2026-08-31); a Windows user still hit it on a sluggish browser.
  [#636][handy-636]: an Electron chat box refused Cmd+V but accepted `Direct`.

## Whispering (Svelte + Tauri, native shell in `apps/epicenter`)

Source at commit `ecba024`, 2026-09. [delivery.rs][wh-delivery],
[clipboard.rs][wh-clip], [keyboard/mod.rs][wh-kb], [sink.ts][wh-sink],
[ADR-0040][wh-adr40], [ADR-0117][wh-adr117].

- Mechanism: enigo Meta press, key code 9 press and release, Meta release
  ([delivery.rs][wh-delivery] 96–114). No AppleScript or typing route.
- Clipboard: 50 ms before the chord, 100 ms after, then restore (18–21,
  76–84). The macOS snapshot copies every item's every type through objc2 and
  restores it verbatim; promised types are skipped ([clipboard.rs][wh-clip]
  1–34, 64–118). The write carries `org.nspasteboard.ConcealedType` (46,
  124–139). No `changeCount` guard. With "keep on clipboard" the restore is
  skipped (50–60).
- Focus: none. Accessibility: `write_text` refuses to paste unless a
  supervisor reports `DictationCapability::Active`, and then leaves the text
  on the clipboard and returns `LeftOnClipboard`, which the UI shows as a
  reduced "reach" (36–48; [sink.ts][wh-sink] 51–87). [ADR-0040][wh-adr40]
  (2026-06): "When the grant is absent the keystroke silently no-ops: the OS
  delivers no event, but the synthetic-input call still reports success. The
  clipboard sandwich … then restores the user's original clipboard, wiping the
  transcript that never pasted." The ADR rejects observing the keystroke,
  typing character by character, and copying on every dictation.
- The supervisor exists because `AXIsProcessTrusted` can say yes while the
  paste is dropped: "a stale post-update grant reads as trusted … yet silently
  drops the paste. The only reliable way to tell a healthy grant from a stale
  one is to run a real tap and watch whether it stays alive"
  ([keyboard/mod.rs][wh-kb] 1–11; [ADR-0117][wh-adr117]). The user-facing
  history: [#150][wh-150] (2024-07) tells macOS users to remove and re-add the
  app in Accessibility; [#284][wh-284] (2024-08) found the paste failed when
  the app's own window went to the background.
- Other issues: [#856][wh-856] (open, Linux) paste lands nothing in a terminal
  running Claude Code; [#1788][wh-1788] a transcript pasted into the wrong app
  after the user switched apps mid-dictation.

## Yap (Swift)

Source at commit `79df0b2`, 2026-09. [TextInjector][yap-inj],
[SecureInput][yap-secure]. Nine commits on 2026-07-23 record each decision.

- Mechanism: AppleScript `keystroke "v" using command down` first; if System
  Events is unavailable, four CGEvents (Command down, V down, V up, Command
  up) 10 ms apart from a `.privateState` source, with `NX_DEVICELCMDKEYMASK`
  (0x8) set alongside `.maskCommand` ([TextInjector][yap-inj] 36–38, 96–142).
  [3db77ae][yap-c-electron]: "Slack and Cursor still ignored the paste … Yap
  posted only a V key event carrying .maskCommand … Chromium rebuilds modifier
  state from the raw event stream, so without a genuine Command keyDown it
  never recognises a Cmd-V and the paste silently does nothing." Automation
  permission is requested at onboarding because AppleScript "proved reliable
  across native, Electron and web apps alike, where synthetic key events only
  ever worked in native ones" ([0bf0ccb][yap-c-as]).
- Clipboard: 30 ms before the paste; restore 100 ms after, only if
  `changeCount` is unchanged and a private session type still holds this
  paste's UUID; `org.nspasteboard.TransientType` is set (31–34, 40–41,
  53–60, 156–170). The delay went 100 ms → 250 ms ([93f2f29][yap-c-restart])
  → 1.5 s ([afa8872][yap-c-cross]: "Chromium-based apps read the pasteboard
  asynchronously and more than once (browser process, then renderer), so an
  early restore hands the renderer stale or empty data") → 100 ms
  ([f577427][yap-c-01], 2026-08: the 1.5 s window let a manual Cmd+V paste the
  transcript twice).
- Focus: the frontmost app is captured when recording starts and re-activated
  before the paste (43–47, 74–77); the paste waits up to 600 ms for the
  hotkey's modifiers to be released (82, 172–180). There is no editability
  gate: "Electron and web apps report no focused element at all, so any such
  gate silently refuses to paste into Slack, VS Code, Discord and friends"
  (87–89). [792ae9a][yap-c-slack] first loosened a role check to "something has
  focus" because "web content routinely reports a generic role with no
  settable AXValue even with the caret in a real text box"; [afa8872][yap-c-cross]
  removed it: "Slack, Cursor, Linear, Notion and Spotify all report no focused
  element at all".
- Guards: without `AXIsProcessTrusted` the text is left on the clipboard;
  when `IsSecureEventInputEnabled()` the text is left on the clipboard and
  the holder's name is reported, found through `kCGSSessionSecureInputPID`
  (62–72; [SecureInput][yap-secure] 8–40).

## Talkify (Swift)

Source at commit `795e412`, 2026-09. [TextInsertionService][tk-svc],
[TextInsertionService+Clipboard][tk-clip].

- Mechanism: V down and V up with `.maskCommand` from a
  `.combinedSessionState` source, no Command key events
  ([TextInsertionService][tk-svc] 403–415).
- Clipboard: snapshot of every item on a background queue with a 600 ms
  timeout, because a promised type from another app "wedged the main actor in
  __dataForType" (92–105, 316–331); the write happens only if `changeCount`
  is unchanged since the snapshot and carries `TransientType` and
  `AutoGeneratedType` ([+Clipboard][tk-clip] 196–230); wait 500 ms (118–120);
  restore only if `changeCount` still equals the value after the write
  (237–246).
- Focus: the focused element is captured when recording starts, with the
  frontmost app as the boundary when there is none ("Some apps expose no
  focused AX element even while an editor has focus", 134–160). Before the
  paste, `isStillFocused` compares the current system-wide focused element
  with `CFEqual`, or the frontmost pid when no element was captured; on a
  mismatch the text is copied instead of pasted (169–198, 289–306). Password
  fields are recognised by the `AXSecureTextField` subrole (222–233). A
  comment on the copy path: "Measured on macOS 26, Chromium browsers report no
  focused element at all and Safari reports a web area with no selected text"
  (351–362).

## What the pasteboard API allows

- `changeCount` "increments each time the pasteboard ownership changes" and
  is returned by `clearContents` and `declareTypes` [apple-changecount]. The
  programming guide: it "increments every time the contents of the pasteboard
  changes (a new owner is declared)" [apple-guide-concepts]. A read does not
  change it, so polling `changeCount` after Cmd+V cannot detect the paste.
  The suggestion to do so in VoiceInk [#610][vi-610] is wrong on this point.
- Lazy data is public API: `declareTypes(_:owner:)` is documented as the
  equivalent of writing the first item and then promising types for it
  [apple-declaretypes]; the owner conforms to
  `NSPasteboardTypeOwner`, whose `pasteboard(_:provideDataForType:)` "Requests
  that the object provide data for the data type" and whose
  `pasteboardChangedOwner(_:)` reports loss of ownership [apple-owner]
  [apple-provide] [apple-changedowner]. The item-based equivalent is
  `NSPasteboardItem.setDataProvider(_:forTypes:)`, "messaged to provide the
  data for any of the specified types when requested" [apple-provider]. This
  is what Handy's receipt-sequenced paste uses; a read receipt is therefore
  observable, and "restore only after the target read the clipboard" is
  possible without private API.
- The `org.nspasteboard.*` types (`TransientType`, `ConcealedType`,
  `AutoGeneratedType`, `source`) are a convention that Maccy, Paste, Alfred and
  others honour [nspasteboard]. VoiceInk, Handy, Whispering, Yap and Talkify
  set some of them.
- Secure event input: while any process has it on, the system stops passing
  keyboard events to event taps and other intercept processes;
  `IsSecureEventInputEnabled` reports the system-wide state [tn2150]. Only Yap
  gates the paste on it.

## What this implies for Type Me It

Problem 2, the previous clipboard being pasted.

- Every clipboard-based project has this bug report, and every fixed delay
  was outrun somewhere: 60–190 ms in Handy [#502][handy-502], 250 and 500 ms
  in VoiceInk [#722][vi-722], 1 s in VoiceInk [#415][vi-415], 100 ms in
  OpenSuperWhisper [#153][osw-153], 250 ms in Yap for Chromium
  ([afa8872][yap-c-cross]). Type Me It's 60 ms after the keystroke is the
  shortest of the set, equal to Handy's legacy default.
- Verified in source: Handy's promise-based restore is the only approach that
  waits for the read itself ([paste_tx/macos.rs][handy-tx-mac]). The Swift
  equivalent is `declareTypes([.string], owner: self)` with
  `pasteboard(_:provideDataForType:)` recording the receipt, then restore
  200 ms after the last receipt, capped, and only if `changeCount` is
  unchanged. Cost: the owner must stay alive and be serviced on the main run
  loop; a clipboard manager that reads eagerly produces a receipt before the
  chord, which Handy discounts by timestamp; a promise is what Whispering's
  and Talkify's snapshots deliberately skip or time out on, so another
  dictation app's snapshot taken during our window sees no text.
- The cheaper change is the one VoiceInk, OpenSuperWhisper, Yap and Talkify
  converged on: a long delay (500 ms to 2 s) plus restore only when
  `changeCount` still equals the value read after our write, ideally with a
  private session type. Type Me It already reads `ourChange`
  (`Output.swift` 33, 42); it needs to skip the restore on a mismatch rather
  than log it. The delay trades against the double-paste window Yap hit at
  1.5 s ([f577427][yap-c-01]).
- Hex's pre-paste wait for `changeCount` to reach the written value
  ([hex-pb] 236–266) addresses a different race, the keystroke arriving before
  the write; it does not touch the restore.
- Not restoring (VoiceInk's default from 2025-12 to 2026-01, Handy's "copy to
  clipboard", Hex's "Copy to clipboard") removes the race and produced the
  opposite complaints ([#432][vi-432], [#646][vi-646]).

Problem 1, a paste that lands nothing.

- Causes found in the other trackers, each with a fix in source: only a V
  event with the Command flag, which Chromium/Electron, Java, Parallels and
  VMware ignore ([3db77ae][yap-c-electron], [#141][osw-141], [#12][handy-12]);
  Type Me It, OpenSuperWhisper and Talkify post only the V event, the other
  six post or hold a real Command key. A stale Accessibility grant after an
  update, which `AXIsProcessTrusted` cannot distinguish ([ADR-0040][wh-adr40],
  [#150][wh-150]); Type Me It's `posted` flag cannot see it either
  (`Output.swift` 9–10). Not secure event input: TN2150 defines its effect on
  processes that intercept keyboard events (HID seize, event taps, `GetKeys`)
  and says nothing about posted events [tn2150]; loginwindow holds it after
  every unlock (`TypeMeIt/SecureInput.swift` 7–9) and pastes land then, so
  Yap's refusal to paste under it ([Yap][yap-inj] 69–72) is a choice, not a
  finding. The V key code not being V on the active layout (VoiceInk
  [cbf7f60][vi-c-layout], OpenSuperWhisper [#90][osw-90], Handy
  [input.rs][handy-input] 77–133). An early restore, which for Chromium's
  asynchronous read turns into an empty paste rather than an old one
  ([TextInjector][yap-inj] 23–27). Apps whose Cmd+V is not paste (Hex
  [#29][hex-29], Handy [#636][handy-636]), where only typing or AX insertion
  works.
- AppleScript `keystroke` is the route two projects reach for when CGEvents
  fail (VoiceInk setting, Yap default). It needs Automation consent and
  `NSAppleEventsUsageDescription`, and does not work under the App Sandbox
  without an entitlement ([#289][hex-289]).
- Inferred, not verified anywhere: none of the projects reads the field back
  to confirm the paste; Type Me It's debug read-back (`Output.swift` 92–126)
  is the only such check in this set, and Talkify's note that Chromium exposes
  no focused element on macOS 26 bounds where it can work.

Problem 3, whether a text field is focused.

- Verified: no project gates the paste on the focused element being editable.
  VoiceInk shipped that gate for a week in 2025-07 and removed it because
  Electron apps fail it ([#159][vi-159]); Yap removed it the day it was
  written, naming Slack, Cursor, Linear, Notion and Spotify as reporting no
  focused element ([afa8872][yap-c-cross]) and web content as reporting a
  generic role without a settable `AXValue` while the caret is in a text box
  ([792ae9a][yap-c-slack]); Talkify measured the same on macOS 26.
- Type Me It's `nil` answer already falls through to the paste. The `false`
  answer (`Focus.swift` 101–105), which triggers the copy prompt, is the case
  Yap's [792ae9a][yap-c-slack] describes for web content, so a copy prompt
  after a paste that in fact landed is expected in browsers and Electron.
- Talkify's alternative answers a narrower question that AX can answer:
  capture the focused element (or the frontmost pid) when recording starts,
  and before pasting check that focus is still the same element
  ([TextInsertionService][tk-svc] 289–306). Yap and speaktype capture and
  re-activate the app instead. VoiceInk has open requests for the same
  ([#803][vi-803], [#928][vi-928]) and Whispering's [#1788][wh-1788] is the
  failure it prevents. Type Me It records the target app for history
  (`Pipeline.swift` 277–278) but does not compare it at paste time.
